## この章のゴール

第6章までは、IP アドレスと MAC アドレスを使って「**どの機器に**届けるか」を見てきました。でも、1台の機器の中では、Web ブラウザ、チャットアプリ、時刻合わせなど、たくさんのプログラムが同時に通信しています。届いたデータを**どのプログラムに渡すか**は、どうやって決めているのでしょうか。

この章では、**UDP** という一番シンプルな通信で、実際に文字を送り合いながら次のことを確かめます。

- 届いたデータを受け取るプログラムを決めるのが **ポート番号**
- 送る側にもポート番号があり、返事はそこに届く
- UDP は**届いたかどうかを確かめない**。届かなくても、送った側は気づかない

## 7-0. 準備

第1章と同じ2台を作ります。

```bash
sudo ip netns add pc1
sudo ip netns add pc2
sudo ip link add veth-pc1 type veth peer name veth-pc2
sudo ip link set veth-pc1 netns pc1
sudo ip link set veth-pc2 netns pc2
sudo ip netns exec pc1 ip addr add 192.168.0.1/24 dev veth-pc1
sudo ip netns exec pc2 ip addr add 192.168.0.2/24 dev veth-pc2
sudo ip netns exec pc1 ip link set veth-pc1 up
sudo ip netns exec pc2 ip link set veth-pc2 up
```

この章では、ネットワーク越しに文字を送受信できる **`nc`**（netcat）というコマンドを使います。Ubuntu 24.04 には最初から入っていますが、無い場合は次で入れてください。

```bash
sudo apt install -y netcat-openbsd
```

## 7-1. ポート番号 —— 建物の中の部屋番号

これまでの章のたとえを続けると、IP アドレスは「町名と番地」でした。番地まで分かれば建物には着きますが、建物の中にはたくさんの部屋があります。**ポート番号は、その部屋番号**です。

- ポート番号は **0〜65535** の数字
- 通信したいプログラムは、自分の部屋番号を決めて「この番号宛てのデータは自分に渡して」と Linux に申し込む（**待ち受け**）
- 届いたデータは、宛先ポート番号を見て、その番号で待ち受けているプログラムに渡される

## 7-2. UDP で文字を送る

`pc2` の 9999 番で待ち受け、`pc1` から文字を送ってみます。

**ターミナル2**（`pc2` で待ち受ける）：

```bash
sudo ip netns exec pc2 nc -u -l 9999
```

`-u` は UDP を使う、`-l` は待ち受ける（listen）、`9999` は待ち受けるポート番号です。実行すると何も表示されずに止まります。データが届くのを待っている状態です。

**ターミナル1**（`pc1` から送る）：

```bash
echo hello | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 9999
```

`echo hello |` で `hello` という文字を `nc` に渡し、`192.168.0.2` の `9999` 番に送ります。`-w 1` は「1秒たったら終わる」という指定です。

ターミナル2に、次のように表示されます。

```text
hello
```

`pc1` から `pc2` の 9999 番で待っていた `nc` に、文字が届きました。

:::message
この章の `nc -u -l` は、**最初にデータを送ってきた相手としかやり取りしない**という性質があります。2回目の `echo ... | nc` は、1回目とは別の相手として扱われ、表示されません。この章では、**送るたびにターミナル2の `nc` を `Ctrl+C` で止めて、起動し直してください**。理由は 7-5 で分かります。
:::

## 7-3. 待ち受けているプログラムを見る

ターミナル2で `nc -u -l 9999` を起動し直してから、さらに別のターミナルで、`pc2` の中でどのポートが待ち受け中かを見てみます。

```bash
sudo ip netns exec pc2 ss -ulnp
```

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
UNCONN 0      0            0.0.0.0:9999      0.0.0.0:*    users:(("nc",pid=1620,fd=3))
```

`ss` はポートの使用状況を表示するコマンドです。`-u` は UDP、`-l` は待ち受け中のもの、`-n` は番号のまま表示、`-p` は使っているプログラム名を表示、という指定です。

`Local Address:Port` が `0.0.0.0:9999` で、`users:(("nc",...))` とあります。「**9999 番は `nc` が待ち受けている**」と読めます。`0.0.0.0` は「この機器のどの IP アドレス宛てでも受け付ける」という意味です。

「サーバのこのポートで、本当にプログラムが待ち受けているか？」を調べるときに、現場で最もよく使うコマンドの1つです。

## 7-4. 観察する —— パケットの中身

ケーブルの上を流れる UDP を見てみます。ターミナルを3つ使います。

**ターミナル3**（`pc2` で `tcpdump`）：

```bash
sudo ip netns exec pc2 tcpdump -n -A -i veth-pc2 udp
```

`-A` は、パケットの中身を文字として表示する指定です。

**ターミナル2**（`nc` を起動し直す）：

```bash
sudo ip netns exec pc2 nc -u -l 9999
```

**ターミナル1**：

```bash
echo hello | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 9999
```

ターミナル3（時刻は省いています）：

```text
IP 192.168.0.1.33561 > 192.168.0.2.9999: UDP, length 6
E..".#@.@..S..........'....shello
```

1行目の住所の書き方に注目してください。`192.168.0.2.9999` は「`192.168.0.2` の **9999 番**」、つまり **IP アドレスの後ろに `.` でポート番号を付けた形**です。

| 部分 | 意味 |
|---|---|
| `192.168.0.1.33561` | 送信元：`pc1` の **33561 番** |
| `192.168.0.2.9999` | 宛先：`pc2` の **9999 番** |
| `UDP, length 6` | UDP で、中身は 6 バイト（`hello` と改行） |

2行目の末尾に、送った **`hello` がそのまま見えています**。UDP は中身を暗号化しないので、途中のケーブルで `tcpdump` されれば、誰でも読めてしまいます。

### 送る側にもポート番号がある

送信元の `33561` は、`pc1` の `nc` が使ったポート番号です。こちらは自分で指定していません。送る側のポート番号は、Linux が空いている番号から**自動で選びます**（**エフェメラルポート**、一時的なポート）。もう一度送ると、たいてい別の番号になります。

## 7-5. 返事は送り主のポートに届く

送る側にもポート番号があるのは、**返事を受け取るため**です。`pc2` から `pc1` に返事を送ってみます。

**ターミナル3**（`pc1` で `tcpdump`）：

```bash
sudo ip netns exec pc1 tcpdump -n -i veth-pc1 udp
```

**ターミナル2**（`nc` を起動し直す）：

```bash
sudo ip netns exec pc2 nc -u -l 9999
```

**ターミナル1**（`-w 1` を付けずに起動し、`ping` と打って Enter）：

```bash
sudo ip netns exec pc1 nc -u 192.168.0.2 9999
```

```text
ping
```

ターミナル2に `ping` が表示されたら、**ターミナル2で `pong` と打って Enter** を押します。ターミナル1に `pong` が表示されます。確認したら、ターミナル1・2とも `Ctrl+C` で止めてください。

ターミナル3（時刻は省いています）：

```text
IP 192.168.0.1.54014 > 192.168.0.2.9999: UDP, length 5
IP 192.168.0.2.9999 > 192.168.0.1.54014: UDP, length 5
```

1行目（`ping`）は「`pc1` の 54014 番 → `pc2` の 9999 番」、2行目（`pong`）は「`pc2` の 9999 番 → `pc1` の 54014 番」です。**返事では送信元と宛先が入れ替わり**、`pc1` が自動で選んだ 54014 番に届いています。`pc1` の `nc` は 54014 番を使っているので、`pong` を受け取れました。

7-2 で「`nc -u -l` は最初の相手としかやり取りしない」と書いたのは、このためです。`nc -u -l` は最初に届いたデータの送り主（この例では `192.168.0.1` の 54014 番）を「会話の相手」と決め、返事をそこへ送ります。別のポート番号から届いたデータは、別の相手からのものなので受け取りません。

## 7-6. ポートで受け取るプログラムを分ける

1台の `pc2` で、2つのプログラムを別々のポートで待ち受けさせます。

**ターミナル2**：

```bash
sudo ip netns exec pc2 nc -u -l 9999
```

**ターミナル3**：

```bash
sudo ip netns exec pc2 nc -u -l 8888
```

**ターミナル1**：

```bash
echo to-9999 | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 9999
echo to-8888 | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 8888
```

ターミナル2には `to-9999` だけが、ターミナル3には `to-8888` だけが表示されます。

```text
to-9999
```

```text
to-8888
```

宛先の IP アドレスは同じ `192.168.0.2` でも、**ポート番号が違えば、別のプログラムに届きます**。1台のサーバで Web と DNS と SSH を同時に動かせるのは、このおかげです。

確認したら、ターミナル2・3の `nc` を `Ctrl+C` で止めておきます。

## 7-7. 壊してみる① —— 誰もいない部屋に送ったら

誰も待ち受けていない 7777 番に送ってみます。

**ターミナル2**（`pc1` で `tcpdump`）：

```bash
sudo ip netns exec pc1 tcpdump -n -i veth-pc1 udp or icmp
```

**ターミナル1**：

```bash
echo hello | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 7777; echo exit=$?
```

```text
exit=0
```

`echo exit=$?` は、直前のコマンドが成功したか（`0` なら成功）を表示します。**`nc` は成功で終わりました**。エラーは何も出ていません。

ところが、ターミナル2（時刻は省いています）を見ると、こうなっています。

```text
IP 192.168.0.1.33743 > 192.168.0.2.7777: UDP, length 6
IP 192.168.0.2 > 192.168.0.1: ICMP 192.168.0.2 udp port 7777 unreachable, length 42
```

`pc2` から **`udp port 7777 unreachable`**（7777 番は使われていない）という ICMP が返ってきています。第6章の `traceroute` の最後に出てきた知らせと同じものです。`traceroute` は、わざと使われていなさそうなポートに送って、この知らせが返ってきたら「宛先に着いた」と判断していたのです。

`pc2` は「その部屋には誰もいない」と知らせてくれたのに、`pc1` の `nc` はそれを気にせず、成功として終わりました。**UDP では、送る側のプログラムが、届いたかどうかを確かめないことがよくあります**。

## 7-8. 壊してみる② —— 受け取る人が後から来たら

今度は、受け取るプログラムが**まだ起動していない**うちに送ってみます。

**ターミナル1**（まだ誰も待ち受けていない 9999 番へ）：

```bash
echo first | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 9999
```

**ターミナル2**（それから待ち受けを始める）：

```bash
sudo ip netns exec pc2 nc -u -l 9999
```

**ターミナル1**（もう一度送る）：

```bash
echo second | sudo ip netns exec pc1 nc -u -w 1 192.168.0.2 9999
```

ターミナル2には、`second` だけが表示されます。

```text
second
```

**`first` は消えてしまいました**。受け取るプログラムがいなかったので `pc2` で捨てられ、誰も送り直してくれません。`pc1` の `nc` も、`first` を送ったときに成功で終わっています。

これが UDP の性質です。

- 相手が受け取ったかどうかを**確かめない**
- 届かなかったデータを**送り直さない**
- そのかわり、準備なしにいきなり送れて、**速くて軽い**

1つや2つ消えても困らない、あるいは消えたら自分で聞き直せばいい用途に向いています。たとえば DNS の問い合わせ（返事が来なければもう一度聞く）、動画や音声の通話（遅れて届いた古いデータは要らない）、時刻合わせなどです。

## 7-9. よく使われるポート番号

よく使われるサービスは、待ち受けるポート番号が慣習的に決まっています（**ウェルノウンポート**）。Linux では `/etc/services` に一覧があります。

```bash
grep -E "^(domain|ntp|syslog|http|https|ssh)\s" /etc/services
```

```text
ssh		22/tcp				# SSH Remote Login Protocol
domain		53/tcp				# Domain Name Server
domain		53/udp
http		80/tcp		www		# WorldWideWeb HTTP
ntp		123/udp				# Network Time Protocol
https		443/tcp				# http protocol over TLS/SSL
https		443/udp				# HTTP/3
syslog		514/udp
```

| 番号 | 名前 | 用途 | UDP / TCP |
|---|---|---|---|
| 22 | ssh | サーバへのリモートログイン | TCP |
| 53 | domain | DNS（名前から IP アドレスを引く。第10章） | 主に UDP |
| 80 | http | Web（第11章） | TCP |
| 123 | ntp | 時刻合わせ | UDP |
| 443 | https | 暗号化された Web | TCP（HTTP/3 は UDP） |
| 514 | syslog | ログの送信 | UDP |

同じ番号でも、UDP と TCP は**別の部屋**として扱われます。表の右端に UDP と TCP が並んでいるのはそのためです。ssh や http が TCP なのは、届かないと困るデータだからです。次の章では、その TCP を見ていきます。

## 7-10. 片付け

ターミナル2・3で `nc` や `tcpdump` が動いていたら `Ctrl+C` で止めてから、片付けます。

```bash
sudo ip -all netns delete
```

## まとめ

- **ポート番号**（0〜65535）は、届いたデータを**どのプログラムに渡すか**を決める部屋番号。`tcpdump` では `192.168.0.2.9999` のように IP アドレスの後ろに付く
- 待ち受け中のポートとプログラムは **`ss -ulnp`**（TCP なら `ss -tlnp`）で確認できる
- 送る側のポート番号は Linux が自動で選ぶ（**エフェメラルポート**）。返事は送信元と宛先が入れ替わって、そこに届く
- 誰も待ち受けていないポートに送ると、**`port unreachable`** の ICMP が返る。ただし送ったプログラムが気にするとは限らない
- **UDP** は届いたか確かめず、送り直さない。そのかわり速くて軽い。DNS・通話・時刻合わせなどに使う
- UDP は中身を暗号化しないので、`tcpdump -A` で**中身がそのまま読める**

7-8 では、`first` が消えても誰も気づきませんでした。Web ページやファイルの一部が黙って消えたら困ります。次の章では、**届いたことを確かめ、消えたら送り直す** TCP の仕組みを、わざとパケットを落としながら観察します。
